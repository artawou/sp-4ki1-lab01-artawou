# ЛР1 — Ізоляційна капсула

## Варіант
Номер у списку групи: **N = 2**  
Розрахунок: `N % 4 = 2`  
Суфікс: `charlie`  
HOST_PORT: `8082`

## Етап 1. Перевірка Docker і запуск чернетки

Команда:
```bash
docker version
docker run -it --name devbox-charlie ubuntu:24.04 bash
```

## Етап 2. Процеси всередині контейнера

Команди всередині `devbox-charlie`:
```bash
echo $$
apt-get update && apt-get install -y curl git procps iproute2
ps aux
```

## Етап 3. Процеси на хості

Команда в окремому терміналі хоста:
```bash
ps aux | wc -l
```

## Контрольні питання

1. **Чому процес у контейнері бачить себе як PID 1?**  
   Тому що контейнер використовує окремий PID-простір і власну нумерацію процесів. Головний процес контейнера має PID 1, хоча на хості той самий процес має інший PID.

2. **Ядро в контейнері те саме, що й на хості? Як це перевірити?**  
   Так, контейнер використовує ядро хостової операційної системи. Версію ядра можна перевірити командою `uname -r`.

3. **Що станеться, якщо звернутися до `http://localhost:8080` з хоста, а контейнер запущено без `-p`?**  
   Зазвичай з'єднання не встановиться, бо порт контейнера не опублікований на хості.

4. **Чим `-p 8080:80` відрізняється від `-p 80:80` з погляду безпеки?**  
   Обидві команди публікують порт контейнера на хості. Порт 8080 зазвичай не є привілейованим, а порт 80 у Linux зазвичай потребує спеціальних прав для прив'язування. В обох випадках опублікований порт може бути доступним ззовні залежно від налаштувань мережі та Docker.

5. **Це один процес чи два різні, якщо всередині `echo $$` показує 1, а на хості інший PID?**  
   Це той самий процес, але він має різні PID у різних PID-просторах. `ps aux` усередині показує процеси контейнера, а `ps aux` на хості може показати процес контейнера під хостовим PID.

6. **Чому Bash-скрипт надійніший за ручний набір команд?**  
   Він зберігає послідовність дій і параметри, тому розгортання можна повторити однаково та зменшити ризик помилок.

7. **Чи буде процес контейнера присутній у `ps aux` на хості?**  
   Так. Хост бачить процес контейнера у власному PID-просторі, де він має інший PID.

8. **Чому `docker rm -f` перед повторним `docker run --name ...` допомагає ідемпотентності?**  
   Він прибирає старий контейнер з таким ім'ям, щоб повторний запуск міг створити його заново без помилки конфлікту імен.

## Рівень 2 — проброс порту

Контейнер з опублікованим портом запускається з параметром `-p 8082:80`. Усередині контейнера запускається HTTP-сервер на порту 80, а на хості перевіряється команда `curl -i http://localhost:8082/`.

Для порівняння повтори запуск без `-p` під іншим ім'ям і перевір, що доступ через порт хоста не працює.

## Рівень 3 — автоматизація

Скрипт `deploy.sh` розміщується в репозиторії `vtfk-sid` за шляхом `core/capsule/deploy.sh`. Він використовує `HOST_PORT=8082` за замовчуванням, видаляє старий контейнер перед створенням нового та встановлює потрібні утиліти.

Перевірка:
```bash
chmod +x core/capsule/deploy.sh
HOST_PORT=8082 ./core/capsule/deploy.sh
HOST_PORT=8082 ./core/capsule/deploy.sh
docker exec vtfk-lab01 bash -lc 'command -v curl; command -v git; command -v ps; command -v ip'
```
